# Which storage path fits a first-generation Pixel?

For a Windows photo library and a rooted Pixel on stock Android 10, start with a read-only Windows SMB share. Rclone speaks SMB on the phone and exposes files through FUSE, the filesystem interface already in the stock kernel. Google Photos opens ordinary paths and reads photo or video bytes across the network. The PC and phone need to stay connected while Photos is reading. [Google kernel configuration](https://android.googlesource.com/kernel/msm/+/72a7a64494e033f2213c9701dbf137d277bf2026/arch/arm64/configs/marlin_defconfig) · [rclone SMB](https://rclone.org/smb/) · [Pixel trial instructions](PC_FOLDER.md)

| Route | Where the originals are read from | Why choose it |
| --- | --- | --- |
| Windows SMB and Android rclone/FUSE | The selected PC folder, in place | Closest to the folder-picker workflow. A contributor reported uploads on both 2016 models on build `QP1A.191005.007.A3`. Large collections can be slow to index. [Hardware report](https://github.com/master-hax/pixel-backup-gang/issues/7) · [Pixel XL experience](https://tautomer.github.io/posts/google_photos_pixel_xl/) |
| Powered USB drive and upstream’s storage mount | A drive attached to the phone | The simplest fallback when the PC needs to disconnect or network scanning is slow. Android 10 with Magisk can use this route on the stock kernel. [Upstream USB guide](https://github.com/master-hax/pixel-backup-gang/blob/7c7c311/docs/EXTERNAL_DRIVES.md) |
| Native NFSv3 and upstream’s mount | A NAS or NFS server on the LAN | Fits an existing NFS library, especially if the FUSE trial is too slow. The stock kernel lacks the NFS client. Upstream ships matching boot images for specific builds. [NFS guide](https://github.com/master-hax/pixel-backup-gang/blob/7c7c311/docs/NETWORK_DRIVES.md) · [Release assets](https://github.com/master-hax/pixel-backup-gang/releases/expanded_assets/0.1.1) |

## What Google documents

Google Photos lists unlimited Original quality at no charge for the first-generation Pixel. Its storage policy describes backups from the device. Google's original Pixel hardware footnote describes photos and videos taken with the phone. None of these pages explicitly covers PC-origin files presented over SMB, NFS or USB. The mount controls how the phone reads a file. Google controls the storage treatment of the uploaded item. Check both a fresh imported photo and a video on the intended account. Google's individual-file limits include 10 GB per video and 200 MB or 200 MP per photo. [Quality by Pixel generation](https://support.google.com/photos/answer/6220791?co=GENIE.Platform%3DAndroid&hl=en) · [Storage policy](https://support.google.com/photos/answer/10100180?hl=en) · [2016 hardware notes](https://support.google.com/pixelphone/answer/16043605?hl=en) · [Backup requirements](https://support.google.com/photos/answer/6193313?co=GENIE.Platform%3DAndroid&hl=en)

Keeping rclone's on-disk content cache off eliminates a deliberate full-file copy to internal flash. Android's media index, thumbnails, Photos databases and temporary files can still generate writes. Upstream's 2 GB temporary-write report used a file manager's Share action. It does not quantify automatic device-folder backup. To measure your phone, compare internal userdata sectors written during a representative video upload with a similar idle period, including delayed writes. Free space can recover after a temporary file is deleted. These counters measure operating-system I/O. Physical wear also depends on the storage controller. [rclone cache modes](https://rclone.org/commands/rclone_mount/#vfs-cache-mode-off) · [Upstream investigation](https://github.com/master-hax/pixel-backup-gang/issues/30) · [Linux block statistics](https://www.kernel.org/doc/Documentation/block/stat.txt)

## On-device result

On November 18, 2026, a physical `sailfish` running stock Android 10 `QP1A.191005.007.A3`, kernel `3.18.137-g72a7a64494e`, Magisk 28.1 and enforcing SELinux backed up two fresh files served directly by Windows over Wi-Fi. The test supplied the generated folder to the picker's `-Folder` parameter. It used the same share creation, read-only permission check and cleanup as the graphical chooser. The Pixel used rclone 1.76.0 and fusermount3 3.18.3 with the file-content disk cache off. USB carried setup and inspection commands. Android routed SMB over `wlan0`, the ADB reverse list was empty, and Windows observed signed SMB 3.1.1 opens for **each filename** from the phone's Wi-Fi address.

The watcher mounted the selection read-only at `/storage/emulated/0/PixelBackup`. The Android shell read the 51,093-byte JPEG and 35,572-byte MP4 through that path and their SHA-256 hashes matched the PC originals. MediaStore indexed both. With backup already enabled for **PixelBackup**, Google Photos 8.1 automatically uploaded both in Original quality and reported that each used zero account storage. Windows then removed the test share and Android detached the mount. After restarting Photos, both items reopened from its main library with the same filenames, backup status, quality and storage treatment. [Wi-Fi JPEG receipt](evidence/wifi-jpeg.png) · [Wi-Fi MP4 receipt](evidence/wifi-video.png)

After the share closed, invoking the installed Magisk boot script relaunched the idle watcher in Android's global mount namespace. The phone stayed powered on throughout this test. [Boot launcher](../android_client/start_pc_watcher.sh)

An earlier trial sent SMB through a USB debugging tunnel to Samba on the PC. It also backed up a 44,481-byte JPEG and a 190,906-byte MP4. Both trials used small samples. Large-file throughput and total internal flash writes from Android and Photos remain unmeasured. [USB-tunneled JPEG receipt](evidence/pixel-jpeg.png) · [USB-tunneled MP4 receipt](evidence/pixel-video.png)

## Using a docked drive

Use the scripts from upstream release `0.1.1`. At review time its convenience installer still downloaded `0.0.9`, and the old ext4 script in this fork put SELinux into permissive mode. The newer upstream ext4 script relabels the drive's files while Android enforcement stays on. [Pinned installer](https://github.com/master-hax/pixel-backup-gang/blob/5c86fdf/install.sh) · [Old fork script](https://github.com/supthunder/pixel-backup-gang/blob/3709bbf/scripts/mount_ext4.sh#L40-L42) · [Updated ext4 script](https://github.com/master-hax/pixel-backup-gang/blob/7c7c311/scripts/mount_ext4.sh#L37-L45)

Put copies under a directory named `the_binding` at the drive root. For a first trial from Windows, an existing FAT32 drive is convenient. Its largest individual file is 4 GiB minus one byte. Use a dedicated ext4 drive for larger supported videos. Choose a powered USB-C OTG hub that can charge this Pixel while powering the drive, and verify both under load. [Upstream USB guide](https://github.com/master-hax/pixel-backup-gang/blob/7c7c311/docs/EXTERNAL_DRIVES.md) · [Hub experiences](https://github.com/master-hax/pixel-backup-gang/discussions/19)

Use the pinned upstream scripts and enter the global mount namespace. For FAT32, supply the actual Android-mounted volume path to `remount_vfat.sh`. For ext4, identify the external partition by filesystem UUID before using `mount_ext4.sh`. The exposed folder is `/storage/emulated/0/the_binding`. The upstream ext4 script recursively changes ownership, permissions and SELinux labels under that folder and gives apps write access. Use a staging drive with the originals retained on the PC. After verification, unmount and eject before disconnecting. [USB setup and commands](https://github.com/master-hax/pixel-backup-gang/blob/7c7c311/docs/EXTERNAL_DRIVES.md#setup) · [ext4 script](https://github.com/master-hax/pixel-backup-gang/blob/7c7c311/scripts/mount_ext4.sh#L31-L54)

For an unattended dock, a one-way transfer from the PC to the attached disk is a useful middle ground. The PC can sleep after this copy finishes. Bind the receiver to the actual removable volume, pause when its identifier disappears, finish each file on that disk before publishing it to Photos, and keep source deletions out of the transfer. An upstream user reports feeding an attached drive with Syncthing. USB automount on insertion is separate from upstream’s NFS boot service. [Docked transfer report](https://github.com/master-hax/pixel-backup-gang/issues/20#issuecomment-2394439392) · [USB automount issue](https://github.com/master-hax/pixel-backup-gang/issues/42)

## When native NFS is worth doing

Upstream release `0.1.1` publishes four NFS-enabled Magisk 30.6 boot images with checksums, for `sailfish` (Pixel) and `marlin` (Pixel XL) on `QP1A.191005.007.A1` or `QP1A.191005.007.A3`. A stock Android 10 phone with an exact device/build match can use the corresponding prebuilt image. Installation changes the active boot image and can replace the existing Magisk setup. Preserve a known-good matching boot image and recovery path before considering a switch. Root alone does not add the missing NFS driver. [NFS guide](https://github.com/master-hax/pixel-backup-gang/blob/7c7c311/docs/NETWORK_DRIVES.md) · [Published images](https://github.com/master-hax/pixel-backup-gang/releases/expanded_assets/0.1.1)

The script requests NFSv3, mounts the export at `/mnt/my_drive`, and exposes its `the_binding` child. It attempts a recursive permission change on that child. For an archive, prepare the child in advance, enforce read-only access on the server, and adapt the helper to request a read-only mount and skip the permission change. The boot module waits for unlock and server reachability. Remounting after a later outage and indexing files added later need their own handling. Windows 10 and 11 client editions do not include Microsoft’s NFS server. A NAS or Linux server is simpler if the library already lives there. [Mount code](https://github.com/master-hax/pixel-backup-gang/blob/7c7c311/scripts/mount_nfs.sh#L67-L113) · [On-device automount report](https://github.com/master-hax/pixel-backup-gang/pull/67) · [Microsoft’s NFS availability matrix](https://learn.microsoft.com/en-us/windows-server/storage/nfs/nfs-overview)
